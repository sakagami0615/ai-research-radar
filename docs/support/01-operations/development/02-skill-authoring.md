# 02 Skill・プロンプトの記述ルール

## 再試行と終了条件

「警告が出たら直して再実行する」と書く場合は、回数の上限、数え方、修正不能時に警告を残して進む条件を明記する。確認できなかった候補など、再実行しても解消できない場合の扱いも示す。

終了コード0での警告に対する再実行は、終了コード1のエラー修正回数へ自動的に含まれるとは限らない。日次Skillの警告への対応・上限は [SKILL.mdの手順5](../../../../skills/agent-daily-run/SKILL.md)、エラー修正の上限・例外・通算範囲は [recovery.md](../../../../skills/agent-daily-run/recovery.md) を正本とする。エラー修正上限だけを根拠に、警告時の無制限ループを許容しない。

## 分割した資料への参照

Skillを複数ファイルへ分ける場合は、どの条件で、いつ、どの資料を読むかを手順本体に明記する。`SKILL.md` と `recovery.md` のような分割で「参照があるときだけ読む」とすると、コマンド失敗時に再実行上限・禁止規則を読み落とすおそれがある。必要な分岐すべてから参照先へ到達できることを確認する。

## シェルのコマンド例

Agentのシェル呼び出しは、変数やカレントディレクトリを次の呼び出しへ引き継がない前提で書く。前の呼び出しで定義した `$code` などに頼らず、一回の呼び出し内で完結させるか、値を `'<http_status>'` のような置換が必要なプレースホルダーにする。

TSVなどのタブ区切りファイルは、Edit／Writeツールでタブが空白に化けることがあるため、`printf '%s\t%s\n' ...` で書かせる。例（表示のみ。実際の値へ置き換え、必要なら検証済みの出力先を指定する）：

```bash
printf '%s\t%s\n' '<url>' '<http_status>'
```

日次の取得ログの列と書き方は [agent-daily-runの手順4](../../../../skills/agent-daily-run/SKILL.md) を参照する。

## レビュー観点の判定条件

レビュー担当の観点は、成果物だけで判定できる条件にする(例: 概要の末尾の注記、取得ログの行)。取得ログのように追記だけされる記録で判定する場合は、「該当する行があるか」ではなく「同じURLの最新の行」で判定する。修正時の再取得で結果が変わっても古い行は残るため、「行があるか」で判定すると、実行Agentが正しく直しても同じ指摘が繰り返され、修正ループが上限まで終わらない。ただし「一度でも本文を取得できたか」のように、消えない事実そのものを判定する場合は行の有無でよい。

## 確認とレビュー

変更後は [テスト実行ガイド](../testing/README.md) に従い、静的な確認と、可能な場合はAgentによる実機確認を行う。レビューの手順と、得られた知見の扱いは [レビュー運用](../review-and-improvement.md) に従う。
