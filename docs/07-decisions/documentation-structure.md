# 文書構成の設計判断

日付: 2026-10-10。状態: ユーザー承認済みの構成を反映。Gitコミットは未実施。

## 問題

旧01〜08は関心事別の技術設計として有用だが、要求・要件、受入、未達と次作業の入口が不足していた。単一ファイル内に概要と詳細、現行と将来が混在し、全体像を読み取りにくかった。

## 決定

要求・要件、基本設計、詳細設計、検証、運用、計画、判断記録を番号付きフォルダへ分け、読む順を明示する。配下は独立して変更・レビューできるテーマで分ける。旧調査資料は08-referenceへ保管する。

必要な結果と受入条件は要件、実現方法は設計、確認手順は検証、対応状態は計画へ置く。資料間は要件IDとリンクでつなぎ、同じ契約をAgent別に複製しない。旧03の共通品質契約は選抜入力ファイルを参照元とする。

## 影響と維持規則

旧仕様の節を移し、[移行対応表](../06-planning/document-migration.md)で追えるようにした。今回の機能実装・品質改善の受入は行わない。

移動時には本文の相対リンクだけでなく、Skill、AGENTS.md、図、章番号だけの参照も確認する。番号付きフォルダの番号と、旧章番号・要件IDを混同しない。受入条件を変更した場合は要件・検証・適用状況を一緒に更新する。

## 要求・要件フォルダ内の分類

ユーザー承認の案1に従い、01-requirements直下はREADMEだけにする。01-needsに背景・利用者・範囲、02-definitionに要件一覧と機能・非機能要件、03-open-questionsに未決定事項を置く。必要な結果を理解してから受入条件へ進む順序である。

初期MVPの成功条件は本フォルダの出典資料へ移し、現在の要件と区別する。今回の再配置では要件ID・受入条件・実装状態を変更しない。
