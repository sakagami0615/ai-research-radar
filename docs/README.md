# AI Research Radar ドキュメント

AI関連の研究・ツール・発表を収集し、根拠付きの日次レポートと記事企画をAIエンジニアの判断につなげる。文書は、必要な結果を合意してから実現方式と確認方法へ進める順に配置する。

## 読む順

| 順序 | 入口 | 答える問い |
| --- | --- | --- |
| 01 | [要求・要件](01-requirements/README.md) | なぜ作るか、誰が使い、何を満たす必要があるか |
| 02 | [基本設計](02-architecture/README.md) | どの構成と責任分担で実現するか |
| 03 | [詳細設計](03-detailed-design/README.md) | 入出力、処理、状態、エラーをどう扱うか |
| 04 | [検証・受入](04-verification/README.md) | 要件を満たしたことをどう確認するか |
| 05 | [運用](05-operations/README.md) | 実行・確認・復旧・改善をどう行うか |
| 06 | [計画・適用状況](06-planning/README.md) | 未達・未確認事項は何で、次の仕事は何か |
| 07 | [設計判断・変更設計](07-decisions/README.md) | なぜその方式を選び、何を変更するか |
| 08 | [参考調査](08-reference/README.md) | 方針の背景と調査根拠は何か |

08は既存調査資料の保存先で、開発の必須工程ではない。各フォルダのREADMEから必要なテーマを読む。数字は読む順であり、開発は要件・設計・検証の間を往復してよい。

## 日次レポート作成の役割分担

![日次レポート作成の役割分担](08-reference/daily-run-flow.svg)

Agent経路ではClaude CodeまたはCodexが共通Skillを読み、Python CLIを実行しながら根拠確認・選抜・文章・企画を作る。一括 `daily` はPythonによる決定論的な経路である。詳しくは [実行経路と責任](02-architecture/workflows.md) を参照。

## 文書の正本と状態

- 必要な結果・受入条件は01、実現方式は02・03、確認方法は04、操作手順は05、未達・未検証の状態は06を正本とする。
- 07の変更設計は目標仕様を含む。現行動作に適用されたとみなす前に、06の適用状況を確認する。
- 要件IDを使って相互参照する。コードが存在すること、CLIへ接続されていること、受入済みであることは分けて記録する。
- Claude CodeとCodexは同じ文書と `skills/` を参照する。Agentごとの設計書を複製しない。

## 再編の範囲

2026-10-10、旧 `docs/specs/01〜09` をテーマ別に分割した。[移行対応表](06-planning/document-migration.md)から旧章の移動先を確認できる。既存の要求を要件IDで整理したが、品質改善の接続や機能追加は実装していない。今回の再編は文書体系の承認に基づき、未決定の数値や新たな機能要件を確定するものではない。
